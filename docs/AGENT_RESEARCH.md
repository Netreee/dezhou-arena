# 扑克 Agent：运行框架、策略表示与研究依据

- 整理日期：2026-10-08。
- 文档性质：前期调研笔记，用于理解工程选择与后续研究方向。
- 证据边界：文献中的成绩均为作者报告；本文件不构成本地复现、训练或竞技水平验收。
- 实现状态：下面的模块、接口职责与实验路线属于设计启示；实际交付以代码和验证记录为准。

## 1. 项目首先需要解决什么

项目希望搭建可接入不同策略的扑克竞技基础设施，再通过实验提高 Agent 的竞技水平。这包含两个可以分别推进的问题：

1. **运行框架是否可靠。** Agent 能否作为普通玩家加入 Arena，经 CLI 获取本人可见信息，调用分析工具，提交合法动作，并留下可核验的运行记录。
2. **策略是否有效。** 在给定规则、筹码深度、对手和成本预算下，Agent 是否能取得更好的长期收益。

运行框架可以先完成，不必先确定双人或六人打法。人数、位置、筹码和完整行动序列必须能够进入观察接口，具体如何使用这些信息由策略决定。框架不应在接口中写死翻前表、模型供应商、提示词格式或求解算法。

### 1.1 各组件的职责

| 组件 | 职责 | 不应承担的职责 |
|---|---|---|
| Arena | 保存权威状态、执行规则、计算合法动作、推进牌局、结算筹码 | 为某个 Agent 提供其他玩家看不到的决策信息 |
| CLI | 提交玩家命令，交付服务端允许该玩家看到的响应，显示操作结果 | 生成对手私牌或绕过规则校验 |
| Agent 运行时 | 管理生命周期、决策时机、工具能力、动作提交与日志 | 规定某种扑克打法 |
| Policy | 依据观察、内部状态和可用工具选择行动 | 直接访问 Arena 的私有状态或数据库 |
| 分析工具 | 执行特定计算或查询，例如牌力、范围、策略表、外部模型调用 | 未经运行时管理直接推进牌局 |
| 评测与训练 | 安排对手、收集轨迹、计算统计量、生成或比较策略版本 | 把一次获胜当作策略改善的证明 |

运行时让每个参赛 Agent 独立成进程，有利于隔离连接、记忆、生命周期和日志。进程数量是部署选择：多个 Agent 仍可调用共享的本地推理服务或远程模型。训练时也可以批量运行多个环境。

本项目要求 Agent 与 Arena 的连接经过既有 CLI。CLI 内部的类型化回调可以交付响应，不需要识别终端排版文字。人类操作、GUI 操作与 Agent 操作应最终走同一个命令解析和玩家视图边界。

## 2. Policy 的含义与表示方式

自然语言里的 policy 通常指指导原则；决策理论里的 policy 是从可知信息到动作的映射。扑克存在隐藏信息和策略随机化，更一般的写法是：

\[
a_t \sim \pi_\theta(a \mid I_t, m_t)
\]

这里的 `I_t` 是玩家在该决策点能够知道的信息，包括本人底牌、公共牌、位置、筹码和公开行动历史；`m_t` 是策略维护的状态，例如此前观察到的对手行为；`θ` 可以是文本、规则参数、策略表或模型权重。

相同公共牌、底池和筹码可能来自不同下注过程。只提供当前快照，会丢失用于估计对手范围的信息。公开行动历史应来自服务端经 CLI 发布的玩家安全信息；不能通过轮询快照差分保证还原，也不能从私有日志补齐。

### 2.1 常见的策略表示

| 表示方式 | 决策机制 | 适合验证的问题 | 主要限制 |
|---|---|---|---|
| 固定自然语言 | 读取 Markdown 等文本，将原则和示例放入模型上下文 | 最低成本地建立 LLM 基线 | 执行一致性、数值推理与策略随机化需要验证 |
| 按场景检索的技能库 | 用位置、牌面、行动线、筹码深度等条件检索适用条目 | 结构化知识是否改善固定提示词 | 检索错误或遗漏会影响决策 |
| 可执行规则与程序 | 代码计算特征、分支和候选动作，可组合 LLM 判断 | 一致性、可复现性和可调试性 | 规则覆盖与启发式偏差 |
| 策略表或求解器 | 查询动作概率、EV、范围，或在当前局面继续求解 | 博弈论策略和实时计算的价值 | 游戏配置匹配、计算成本及抽象误差 |
| 自动优化的上下文 | 用批量反馈更新提示词、示例或结构化条目 | 不更新权重时能否提升策略 | 反馈噪声、调参过拟合、条目退化 |
| 训练后的网络或 LLM | 监督学习、模仿学习、自博弈或强化学习更新权重 | 能否内化更强的决策能力 | 数据、算力和评价成本 |

这些方式可以组合。自然语言条目解释场景和约束，程序计算数值，求解器提供动作分布，模型整合信息。组合是否有效需要模块消融和完整对局检验。

### 2.2 对 Policy 接口的启示

公共接口应表达“决策需要什么、能够做什么、最终产生什么”，把内部表示留给实现。具体建议如下：

- **观察具有明确类型和可见性。** 至少包含本人安全视图、完整公开历史、规则与金额语义、合法动作，以及足以识别当前决策点的信息。
- **策略内部状态独立。** LLM 会话、对手模型、RNG、技能缓存或网络权重不应成为所有 Policy 都必须拥有的公共字段。
- **工具以能力接口提供。** Policy 可以使用零个或多个分析工具。框架管理可用工具、调用失败和记录方式，不要求所有策略都走语言模型工具调用协议。
- **确定动作和混合策略都可表达。** 规则策略常返回一个动作；策略表或网络可能返回概率分布。返回契约应明确定义金额、概率与非法输出的处理。
- **决策和执行有清晰顺序。** 读取观察、调用工具、产生决策、校验、提交 CLI、接收确认；工具调用不应偷偷产生第二条下注通道。
- **运行成本可记录。** 延迟、工具调用、已知 token usage 和已知费用可以作为可选观测数据；不应要求规则策略伪造 LLM 指标。
- **可测试不等于可复现所有外部系统。** 本地采样可注入种子，外部模型调用则记录版本与配置。不能承诺远程模型逐 token 重现。

“LLM 温度较高”不等于“实现了校准的混合策略”。若某局面要求按概率跟注或加注，应由明确的分布与采样规则表达。对策略无关框架而言，允许确定动作同样重要。

## 3. 专业扑克 AI 已验证的构建范式

专业扑克 AI 的主要研究路线包括博弈论策略计算、自博弈、神经网络近似和对局时搜索。它们说明了强策略可以如何构建，并不意味着把论文算法接入接口就自动拥有同等水平。

| 研究 | 核心范式 | 对项目的启示与适用边界 |
|---|---|---|
| [Libratus，Science 2018](https://www.science.org/doi/10.1126/science.aao1733) | 预先计算策略、对局中的子博弈求解与策略改进 | 双人无限注强实战系统；策略实现可能需要对局时计算 |
| [DeepStack，Science 2017](https://www.science.org/doi/10.1126/science.aam6960) | 持续重求解，使用学习到的价值估计限制搜索深度 | 双人无限注；观察历史、范围与数值工具比单一文本提示更接近其输入需求 |
| [Pluribus，Science 2019](https://www.science.org/doi/10.1126/science.aay2400) | 自博弈策略蓝图与对局时有限前瞻搜索 | 六人无限注的强实证结果；多人框架应支持对手组合与位置变化 |
| [Deep CFR，ICML 2019](https://proceedings.mlr.press/v97/brown19b.html) | 用深度网络近似反事实遗憾与平均策略 | 表明 Policy 可以是网络；训练过程不必放进运行时接口 |
| [ReBeL，NeurIPS 2020](https://arxiv.org/abs/2007.13544) | 在公共信念状态上结合强化学习与搜索 | 论文包含扑克实验；[公开仓库](https://github.com/facebookresearch/rebel)仅提供 Liar's Dice 实现，不能当作现成德扑求解器 |
| [Student of Games，Science Advances 2023](https://www.science.org/doi/10.1126/sciadv.adg3256) | 搜索、自博弈学习与博弈论推理相结合 | 支持跨博弈构建的思路，但每个游戏仍需正确的环境与信息结构 |
| [AlphaHoldem，AAAI 2022](https://ojs.aaai.org/index.php/AAAI/article/view/20394) | 端到端深度强化学习，与历史策略版本自博弈 | 对手池、策略版本和训练轨迹应能在运行框架外组织 |

两人零和游戏中的 CFR 收敛、平均策略和可利用性分析有特定前提。六人无抽水牌局也可以保持筹码总和为零，但不能因此直接套用两人零和的理论保证。多人系统的实际成绩与理论保证需要分别表述。

## 4. LLM Agent 的近期相关方法

### 4.1 PokerSkill：结构化技能和确定性上下文

[PokerSkill，2026 年预印本](https://arxiv.org/html/2605.30094)与“Markdown policy 如何进一步增强”的问题最接近。它使用确定性的上下文引擎提取牌面、牌型、位置、行动历史和筹码底池比等特征，再从专家设计的分层技能库中选取适用片段。程序提供当前局面的候选动作与金额边界，LLM 选择动作，最终输出由代码检查。其部署阶段不调用均衡求解器。

论文报告，同一模型对 GTO Wizard 的表现从普通提示词的 `−132 ± 25 mbb/hand` 改善到 `−57 ± 21 mbb/hand`，相当于约 `−13.2 ± 2.5 bb/100` 改善到 `−5.7 ± 2.1 bb/100`；原文的 ± 为一个标准误。

**这个结果仍然亏损，且是双人无限注实验。** 它为结构化技能优于该实验中的普通提示提供证据，不证明六人水平，也不证明达到或超过求解器水平。策略性候选动作剪枝可能排除好动作，应能单独替换和检验。

可以借鉴的决策顺序是：

```text
玩家安全观察与公开行动历史
  → 确定性特征计算
  → 场景技能检索
  → 必要的数值工具调用
  → 结构化决策
  → 校验与 CLI 提交
```

### 4.2 ToolPoker：让工具携带策略信息

[ToolPoker，2026](https://arxiv.org/html/2602.00528)让 LLM 调用统一的求解器工具，使用动作建议、范围和辅助数值，并训练工具使用能力。

其主要实验包括 **Leduc Hold'em 和限注 Texas Hold'em**，不能直接外推到完整无限注六人桌。可迁移的工程经验是：工具除了计算基础牌力，还可以承载策略知识；LLM 负责选择和整合工具返回的信息。

### 4.3 上下文、技能库和提示词也可以优化

| 方法 | 可借鉴之处 | 迁移到扑克时需要验证的部分 |
|---|---|---|
| [DSPy](https://arxiv.org/html/2310.03714v1) / [GEPA，ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/file/0e9e708b6f48e14fd0ac29e167413f76-Paper-Conference.pdf) | 将模型调用组织成有输入输出契约的模块，通过轨迹与评价反馈优化提示词、示例或配置 | 评价噪声、计算预算和对测试对手的过拟合 |
| [ACE，ICLR 2026](https://arxiv.org/html/2510.04618v3) | 维护可积累和修订的结构化 playbook，减少反复重写造成的有用信息丢失 | 新条目是否由足够证据支持，更新后是否改善对局 |
| [Voyager，作者项目](https://voyager.minedojo.org/) | 保存、检索、组合可执行代码技能 | 原实验是 Minecraft，扑克技能与成绩需要另行验证 |
| [From Agent Failures to Text Policies，2026](https://arxiv.org/html/2607.20668) | 区分执行已有策略与从失败中学习策略的能力 | 从失败轨迹生成的文本策略并不必然优于固定提示 |

扑克中的单手收益噪声很大。“输了这手，所以修改策略”不足以支持有效学习。文本优化同样需要批量实验、保留测试集，或使用适用条件明确的决策 EV 评价。

### 4.4 权重训练与执行／训练分离

[SpinGPT，2025](https://arxiv.org/html/2509.22387v2)提供了专家牌谱监督学习和求解器指导后续训练的实例。其短筹码 Spin & Go 训练背景与深筹码部署存在差异：论文描述模型在 200BB Slumbot 环境中过度全下，需要加入深筹码启发式修正；报告的 Slumbot 成绩对应经过修正的 SFT 版本。

因此，规则、筹码深度和训练分布必须明确记录；不应把一个配置下的结果泛化到所有牌局。

[Agent Lightning，2025](https://arxiv.org/abs/2508.03680)将 Agent 执行与训练分开，以标准化轨迹和奖励接口连接两者。原始实验主要是 SQL、检索与数学工具任务，对本项目的价值主要在工程组织：记录观察、工具调用、动作、结果和策略版本，使以后的训练器能够消费这些数据。

## 5. 双人和六人：框架可以统一，策略与评测仍有差异

| 维度 | 双人无限注 | 六人无限注 |
|---|---|---|
| 运行框架 | 观察、决策、工具、提交、日志 | 同样的协作边界 |
| 输入结构 | 一名对手与较简单的位置关系 | 多名对手、位置、多人底池和不同资格状态 |
| 策略建模 | 主要估计一名对手的范围与回应 | 多人的范围、后续行动依赖与参战概率 |
| 理论与分析 | 两人零和均衡和可利用性分析较清晰 | 两人结论不能直接套用 |
| 实验安排 | 可交换座位并使用配对牌序 | 需记录座位、对手组合与多人交互 |
| 推进价值 | 便于隔离问题、标定方法 | 检验最终多人竞技能力 |

运行框架可以把人数作为比赛配置，用可变长度玩家集合与公开行动历史表示牌局。先做双人实验是一种方便的研究顺序，不应成为仅支持双人的接口约束。

## 6. 如何证明一个 Agent 更强

对现金局式目标，首要指标是长期平均净收益，例如 `bb/100`，并同时给出样本量与不确定性。赢下多少手牌容易受到打法影响：多赢小底池、少数时候输大底池，可能仍是亏损策略。

最低限度的实验报告需要包含：

- 规则、盲注、人数、初始或有效筹码深度、有无抽水，以及每手重置还是跨手结转。
- Policy 版本、模型和推理配置、工具版本、种子及对手池组成。
- 手数、净收益、`bb/100`、置信区间或明确的标准误定义。
- 座位安排、配对牌序或其他方差降低设计，以及统计分析的独立采样单位。
- 非法动作、超时、未完成牌局、进程失败和缺失数据的数量与处理方法。
- 延迟、模型调用量、实际 token usage 和已知费用；未知费用保留为空。

适用时可以使用最佳回应、可利用性或求解器决策 EV 辅助评价。完整无限注的精确可利用性计算可能不可行，不能用一个简化近似值冒充精确指标。

[PokerBench，AAAI 2025](https://arxiv.org/html/2501.08328v2)适合检查局部决策能力；动作题准确率不能独立证明完整对局实力。[GTO Wizard Benchmark，2026](https://arxiv.org/abs/2603.23660)可作为双人完整对局与方差降低评价的参考。

本项目已有的跨手筹码结转模式，与每手固定筹码深度的论文基准不同。两者均可研究，但比较必须匹配条件。若目标以后变成锦标赛，需要重新定义名次或奖金效用。

## 7. 对工程实现的优先级建议

### 7.1 首先搭建策略可替换的运行框架

1. 规定 Policy 的观察、工具能力、决策返回值、内部状态和生命周期契约。
2. 通过现有 CLI 连接 Arena，保持普通玩家的信息边界与命令语义。
3. 明确决策触发、命令提交、服务端确认、失败和关闭的顺序。
4. 接入项目统一日志，记录决策与工具调用，同时保留私牌和敏感配置的边界。
5. 用不同内部实现的最小策略检验接口，例如无状态规则策略、有状态策略和使用工具的策略。

这一步的验收是独立进程可以经真实 CLI 完成合法对局、观察和确认正确、策略可替换。它不宣称提高竞技水平。

### 7.2 再建立基线、评价与策略实验

先建立被动、合法随机、明确规则和固定文本等可比较基线，再检验场景技能检索、数值工具和求解器。每增加一个组件，都应说明要验证的问题及关闭它时的对照组。

如果问题集中在上下文组织与知识检索，可研究 GEPA 或 ACE；如果问题是数值策略质量，可研究求解器、策略表或训练后的网络；如果目标是让 LLM 本身掌握工具与决策，再推进监督微调和强化学习。

[LangGraph 官方工作流文档](https://docs.langchain.com/oss/python/langgraph/workflows-agents)可用于理解显式状态工作流；首版简单运行时可以直接用 Python 实现。[OpenSpiel 算法文档](https://openspiel.readthedocs.io/en/stable/algorithms.html)可供 CFR、Deep CFR、NFSP、最佳回应与可利用性研究参考。选择某个框架不会自动提供适配本项目规则的强策略。

最终需要分别报告四件事：框架接入是否完成、工具与策略是否真实执行、完整对局是否通过、竞技水平是否有统计证据。这四项证据不能互相替代。
